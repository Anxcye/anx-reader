# 阅读闭环剩余工作

## 状态

- Status: Proposed
- Priority: P1
- Target release: Unscheduled
- Scope: Reading Agent Beta、三类阅读闭环、阅读成果、多设备恢复
- Architecture reference: [`../architecture/ai-architecture.md`](../architecture/ai-architecture.md)
- Product decisions: [`../../DESIGN.md`](../../DESIGN.md)

## 背景

当前实现已经形成“目标 → 阅读现场 → 章节 checkpoint → 掌握度/难点/记忆/Artifact → 复习卡/阅读成果 → 跨会话与跨设备恢复”的可用主链路。剩余问题不在于缺少更多 AI 按钮，而在于已有成果没有完全回流到全书完成、下一步行动、个性化策略和成本优化。

本文只记录尚未闭合的部分。现有低打扰、用户确认、来源追溯、剧透边界、可撤销写入和本设备位置优先规则继续生效。

## P1：全书完成与成果归档

### 缺口

当前只有会话和章节生命周期，没有稳定的“完成本书”状态。阅读成果页是持续仪表盘，但没有最终收口目标、难点、掌握度、小说悬念和后续行动。

### 目标行为

- 增加用户主动触发的“完成本书”入口，不根据 100% 进度自动完成。
- 完成前展示本地预览：目标状态、未处理 checkpoint、未解决问题、到期卡片和小说未解悬念。
- 用户可选择“先处理”“保留未解决并归档”“取消完成”，不得阻塞正常退出阅读。
- 归档保存完成时间、最终目标判断、用户总结、保留问题和下一步计划。
- AI 总结必须由用户确认后调用，且只读取用户确认的已读安全范围。
- 归档结果进入“本书阅读成果”，可跨设备同步；AI 写入继续支持撤销。

### 完成标准

- 读到 100% 不会自动弹窗、调用模型或完成目标。
- 用户可以在无 AI 配置时完成本书并保存本地归档。
- 未解决项不会因完成本书而丢失。
- 同一书只存在一个当前归档版本，后续修改保留更新时间和冲突规则。

## P1：统一下一阅读行动

### 缺口

成果页已经能用文字提示下一步，但缺少可执行、可排序、可完成的统一行动模型，成果还不能稳定驱动下一次阅读。

### 目标行为

新增声明式 `NextReadingAction` 投影，不新建 AI 任务队列。候选来源包括：

1. 已到期知识卡。
2. 待处理章节 checkpoint。
3. 未解决难点或悬念。
4. 活跃目标的下一范围。
5. 小说恢复上下文或档案覆盖缺口。
6. 全书完成后的行动计划。

每项包含稳定 ID、来源类型、书籍、目标位置、优先级原因、可执行动作和完成判定。优先级由本地确定性规则计算，AI 只能解释或生成建议，不能静默改变排序。

### 完成标准

- 阅读成果页和下次进入阅读时显示同一个首要行动。
- 点击行动能直接进入复习、checkpoint、来源位置或档案整理流程。
- 完成后列表立即重算，不残留已完成行动。
- 小说沉浸闭环不会因知识型默认规则出现强制测验。

## P1：Reader Profile 学习回流

### 缺口

Profile 的候选、三会话证据、确认、拒绝和 90 天抑制已经存在，但生产阅读行为尚未完整接入证据采集，也没有验证确认偏好是否真正改变了后续 Agent 表现。

### 目标行为

- 只采集少量可解释信号：解释深度调整、定义/例子顺序、追问/直接解释选择、输出结构和介入容忍度。
- 行为推断必须跨至少三个不同会话；明确表达可立即生成候选。
- 候选卡说明“观察到什么”和“将改变什么”，确认后才进入 Agent 上下文。
- 每次 prompt 构建记录实际采用的已确认 profile keys，便于验证和排错。
- 用户能够撤销确认、恢复默认；拒绝后 90 天不重复建议。
- 明确 CloudBase 增量同步规则，使同一账号设备共享已确认 Profile，但候选行为证据不必同步。

### 完成标准

- 三个独立会话前不会出现行为推断候选。
- 确认后下一次同类回答可验证采用了该偏好。
- 关闭 Reading Agent Beta 后不继续采集行为证据。
- 其他设备同步后获得 confirmed/rejected 状态，不把未确认候选当作用户事实。

## P2：小说悬念—线索—揭示闭环

### 缺口

当前可以建立悬念、线索和事件 Artifact，但缺少清晰的悬念解决入口和“悬念 → 线索 → 揭示”关系。

### 目标行为

- 支持将 `fiction.clue` 和 `fiction.event` 关联到一个或多个 mystery ID。
- 用户可标记悬念为“已揭示”“暂时解释”“放弃追踪”，AI 只能建议状态变化。
- 悬念详情按正文出现顺序展示线索与揭示，保持 `visibleFromProgress` 剧透过滤。
- 返回早期位置时，后文解决状态和揭示内容必须隐藏；同步时间不得影响展示边界。
- 人物关系图和时间线只消费统一 Artifact 投影，不建立第二套真相表。

### 完成标准

- 可以从未解悬念跳到相关线索和来源。
- 解决状态可撤销、可同步且不会泄露未来内容。
- 同一线索可以关联多个悬念，删除或撤销不会留下失效引用。

## P2：Token 成本归因与优化回路

### 缺口

当前只统计本月输入、输出、合计和请求数，尚不能回答哪个能力、哪本书或哪种模型消耗最多，也不能验证优化是否有效。

### 目标行为

- usage 增加低基数来源标签：chat、translation、reading-agent、fiction-backfill、note-organizer。
- 可选记录 provider、model、是否估算；不记录 prompt 正文、API Key 或敏感选区。
- 小说整理确认页给出预计输入规模和批次数，不伪装成供应商账单价格。
- AI 设置显示按能力和模型的本月汇总，以及真实 usage/估算 usage 比例。
- 优化前后可比较平均每请求 Token、失败重试开销和小说每章消耗。

### 完成标准

- 每个统一 runner 请求恰好计入一个来源，不重复统计重试流片段。
- 未提供服务端 usage 时明确显示估算。
- 清空用量不会影响 AI 会话、阅读成果或同步数据。

## P2：闭环健康度与可观测性

### 目标

使用本地匿名计数验证闭环是否真正被用户完成，而不是只验证页面存在。建议指标：

- 建立目标后形成至少一个成果的比例。
- checkpoint 创建到处理的时长和积压数量。
- 到期卡片实际复习率。
- 未解决问题被处理或带入归档的比例。
- 下一行动展示后被执行的比例。
- 小说档案覆盖与当前安全边界的差距。

这些数据默认只在本机展示，不上传遥测；若未来引入远端分析，必须另行获得明确同意。

## 实施顺序

1. 先定义 `BookCompletionArchive` 与 `NextReadingAction`，让成果能够收口并回流。
2. 接通 Reader Profile 的证据采集、prompt 生效记录和 confirmed 状态同步。
3. 在统一 Artifact 模型上补小说悬念关联与解决状态。
4. 为 Token usage 增加来源归因，再用数据优化上下文和批处理。
5. 最后增加本地闭环健康度，验证前述能力是否真正形成持续使用。

## 非目标

- 不增加后台主动唤醒或自动云端分析。
- 不使用完成率强迫用户复习、测试或写总结。
- 不引入向量数据库、跨书知识图谱或自动 Skill 学习。
- 不让全局最远设备进度自动改变本设备位置或故事整理上限。
- 不用 AI 推断替代用户的掌握度、偏好确认或全书完成判断。
